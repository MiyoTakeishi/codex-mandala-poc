# Codex開発運用ルール

このドキュメントは、Codexにプロジェクト開発を依頼するときの共通ルールをまとめたものです。
他のCodexプロジェクトへコピーして、作業開始時にCodexへ「`docs/AGENT.md` を参照して進めてください」と伝えることで、同じ運用に寄せられます。

## 基本方針

- 計画書がある場合は、計画書の実装順序に沿って進める。
- このプロジェクトでは `docs/` 配下を仕様の正とする。
- 実装は必ず `docs/implementation-plan.md` に従って進める。
- 計画にない実装は行わない。
- 一度に複数機能を実装しない。
- 機能単位で作業する。
- 作業前に、これから実施する内容を短く説明する。
- 既存コード構造を優先し、不要なリファクタリングは行わない。
- 推測ベースの実装は禁止し、必ず仕様または計画に基づく。
- 仕様が不足している場合は、不足点を明示してユーザーに確認する。
- 外部サービスの管理画面操作はCodexが実施しない。必要な作業、設定値、手順をドキュメントまたはメッセージで提示する。
- ユーザー確認が必要な作業は、勝手に先へ進めず、必要なタイミングで明示する。
- 実装後は、可能な範囲でビルド、テスト、動作確認を行う。
- 確認できなかった項目は、理由と残タスクを明記する。

## 仕様参照ルール

- 仕様は `docs/` 配下を正とする。
- 不明点があれば、実装前に `docs/` 配下の仕様、基本設計、実装計画を確認する。
- 仕様に存在しない内容は実装しない。
- 仕様が不足している場合は、不足している判断材料を明示してユーザーに確認する。
- コードとドキュメントが矛盾する場合は、ドキュメントを優先し、必要ならユーザーに確認する。

## 計画書の扱い

- `docs/implementation-plan.md` などの計画書がある場合、最初に読む。
- 現在どのPhase、どの機能にいるかを確認してから作業する。
- 計画書の順序を飛ばす必要がある場合は、理由を説明してから進める。
- 計画書にない作業が必要になった場合は、関連するPhaseの補助作業として扱うか、ユーザーに確認する。
- 機能が完了したら、次に進む前にコミット候補を提示する。

## ブランチ運用

- 作業開始前に現在のブランチと作業ツリーを確認する。
- 変更前に `git status --short --branch` を確認する。
- 未コミット変更がある場合、ユーザーの変更を勝手に戻さない。
- 新しい機能を始める前に、必要に応じてブランチ切り替えや新規ブランチ作成を提案する。
- 作業内容が現在のブランチ目的と合わない場合は、適切なブランチへの切り替えを提案する。
- ブランチ切り替えは原則として提案のみ行う。
- ユーザーが明示的に許可した場合に限り、Codexが `git checkout` / `git switch` を実行してよい。
- ブランチ切り替え前に、作業ツリーがクリーンか確認する。
- ユーザーがプッシュを主導する場合、Codexは勝手に `git push` しない。
- プッシュすべき区切りでは「今プッシュしてよいタイミングです」と伝え、コマンドを提示する。

## Git操作ルール

- Codexは、ユーザーの承認なしにコミットしない。
- 機能完成後、Conventional Commits形式のコミットメッセージ候補を提示する。
- ユーザーが承認したら、対象ファイルをステージしてコミットする。
- ステージ前に対象ファイルを確認する。
- コミット前に `git diff --cached --stat` と `git status --short` でステージ内容を確認する。
- コミット後に `git status --short --branch` を確認する。
- 複数の無関係な変更を1コミットに混ぜない。
- ユーザーが作成した変更や未関係の変更を勝手に戻さない。
- `git reset --hard` や `git checkout -- <file>` など破壊的操作は、明示的な依頼がない限り行わない。

## コマンド実行ルール

ユーザー確認なしで実行してよいコマンド:

- `git status`
- `git log`
- `git diff`
- `git branch`
- `git remote -v`
- ファイル検索、ファイル読み取り
- `npm run build` など、副作用がローカル生成物に限定されるビルド
- `npm test`、`npm run test`、`npm run test:rules`、`npm run test:e2e`
- lint、format系コマンド

条件付きで確認が必要なコマンド:

- `npm install`
  - 初回実行、依存関係追加、ロックファイル更新を伴う場合は事前に説明する。
- buildコマンド
  - デプロイやproduction反映など外部副作用がある場合は確認する。

必ずユーザー確認を取るコマンド:

- `git commit`
- `git push`
- `git checkout` / `git switch`
- `firebase deploy`
- production反映操作
- DB更新、DB削除などデータに影響する操作

## コミットメッセージ

Conventional Commitsを使う。

例:

```text
feat: add chart deletion UI
fix: handle missing updated timestamp
style: refine chart block colors
test: add shared chart e2e tests
docs: add hosting deployment checklist
chore: update firebase config
```

主な使い分け:

- `feat`: 新機能追加
- `fix`: 不具合修正
- `style`: 見た目、CSS、UI調整。挙動変更が主目的ではないもの
- `test`: テスト追加、テスト修正
- `docs`: ドキュメントのみの変更
- `chore`: 設定、依存関係、補助作業
- `refactor`: 外部挙動を変えない内部構造変更

## 作業前説明

作業に入る前に、以下を簡潔に説明する。

- どの計画項目を進めるか
- 今回の作業範囲
- 変更予定の主なファイル
- 外部設定やユーザー操作が必要になりそうか

例:

```text
次はPhase 7のE2Eテスト追加に進みます。
今回はPlaywright設定と共有リンク閲覧の主要フローだけを追加し、Firebase Console操作や本番デプロイは行いません。
```

## 実装中の進め方

- まず既存コードを読む。
- 既存の設計、命名、ディレクトリ構成に合わせる。
- 必要最小限の変更に絞る。
- 途中で重要な方針変更が必要になったら説明する。
- 30秒以上かかる作業では、進捗を短く共有する。
- UI変更では、既存の見た目やユーザーからのフィードバックを優先する。
- Firebaseなど外部状態に依存する作業は、ローカルでできる範囲とユーザーが行う範囲を分ける。

## 検証ルール

実装内容に応じて、必要な検証を行う。

代表例:

```bash
npm run build
npm run test
npm run test:rules
npm run test:e2e
npm --prefix functions run build
```

注意:

- すべてのコマンドが常に必要とは限らない。
- UIのみの小変更ならビルド中心でよい。
- RulesやFirestore権限に関わる変更では `test:rules` を優先する。
- E2E対象の主要フローに関わる変更では `test:e2e` を実行する。
- 失敗した場合、原因が今回の変更か既存設定かを切り分けて説明する。

## Firebase運用ルール

- Firebase Consoleでの設定はCodexが行わない。
- Firebase CLIによる本番デプロイも、ユーザー主導を基本とする。
- Firebase Consoleなど外部サービスの管理画面操作は禁止する。
- Codexは、必要なタイミングで以下を説明する。
  - 何を設定する必要があるか
  - 目的
  - どの画面で設定するか
  - 必要なデータは何か
  - 必要なパラメータ、ID、Key、URL
  - 実行するコマンド
  - 設定後に確認すること
- Firestore Rules、Indexes、Functions、Hostingのデプロイが必要な場合は、明確に手順を提示する。

例:

```bash
npx firebase deploy --only firestore:rules
npx firebase deploy --only firestore:indexes
npx firebase deploy --only functions:addEditor
npx firebase deploy --only hosting
```

コマンドはPowerShellで改行により分割されると失敗することがあるため、1行で提示する。

## 外部設定が必要なときの説明形式

外部設定が必要になったら、以下の形式で説明する。

```text
Firebase Consoleで以下を設定してください。

必要な設定:
- Googleログインを有効化
- 承認済みドメインにHostingドメインを追加

必要なデータ:
- Firebase HostingのURL
- サポートメール

設定後の確認:
- Googleログインできる
- users/{uid} が作成される
```

## ユーザー確認とコミットの流れ

基本フロー:

1. Codexが作業内容を説明する。
2. Codexが1機能を実装する。
3. Codexが検証する。
4. Codexが変更内容、検証結果、コミット候補を提示する。
5. ユーザーが確認する。
6. ユーザーが「ステージとコミットをお願いします」と承認する。
7. Codexがステージしてコミットする。
8. Codexがコミットハッシュと作業ツリー状態を報告する。

## プッシュの流れ

- Codexは勝手にプッシュしない。
- 機能ブランチの区切り、または複数コミットがまとまったタイミングでプッシュを提案する。
- ユーザーがプッシュを行う。
- Codexはプッシュ後に次の作業へ進む。

例:

```text
このブランチは区切りがよいので、今プッシュしてよいタイミングです。

git push -u origin feature/example
```

## レビューや不具合報告への対応

- ユーザーがエラーや画面の問題を報告した場合、まず原因を切り分ける。
- エラーメッセージ、対象ファイル、発生操作を確認する。
- 再現できる範囲で修正する。
- 修正後、同じ操作に対応する検証を行う。
- 不具合修正も1機能として扱い、完了後にコミット候補を提示する。

## ドキュメント更新

- 外部設定、デプロイ手順、運用ルールが増えた場合は、必要に応じて `docs/` に反映する。
- ドキュメントだけの変更は `docs:` コミットにする。
- 実装とドキュメント更新が密接に関係する場合でも、無関係な大きい変更は分ける。

## ドキュメント駆動開発

- `docs/` 配下を唯一の正とする。
- `docs/implementation-plan.md` を実装優先順位の基準にする。
- コードよりドキュメントを優先する。
- 速度よりも、仕様準拠、段階的開発、再現性、事故防止を優先する。

## 安全ルール

- 破壊的変更は禁止し、必要な場合は必ず事前説明と承認を得る。
- 影響範囲が不明な変更は行わない。
- 最小変更で目的を達成する。
- 推測実装をしない。
- 既存のユーザー変更を勝手に戻さない。

## Codexへの依頼文例

作業開始時:

```text
docs/AGENT.md と docs/implementation-plan.md を参照し、ルールと計画書に沿って実装を進めてください。
```

コミット依頼時:

```text
確認できました。ステージとコミットをお願いします。
```

プッシュ判断:

```text
今プッシュしたほうがいいですか？
```

外部設定完了報告:

```text
npx firebase deploy --only firestore:rules を実行しました。ステージとコミットをお願いします。
```

## 最重要ルール

- 計画に沿う。
- 1機能ずつ進める。
- 作業前に説明する。
- 完了後にコミット候補を提示する。
- 承認後にだけコミットする。
- Codexは勝手にプッシュしない。
- 外部サービス設定は手順化し、ユーザーが実施する。
- ユーザーの未コミット変更を勝手に戻さない。
